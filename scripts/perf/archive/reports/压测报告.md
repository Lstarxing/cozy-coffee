# CozyCoffee 性能与并发正确性测试报告

测试日期：2026-09-17（Asia/Shanghai）  
被测提交：`94361cf5316bdb9d0490f7a91645ea6dcea75389`

## 1. 结论摘要

1. 菜单稳态缓存收益明确。在相同 20 RPS、每种模式 5 轮、每轮 60 秒的开放模型测试中，L1 + Redis 相比 DB 直读：
   - 平均响应时间中位数从 40.879 ms 降至 3.956 ms，降低 90.32%；
   - P95 从 64.610 ms 降至 5.909 ms，降低 90.85%；
   - P99 从 90.488 ms 降至 8.005 ms，降低 91.15%；
   - 所有对照组均为 0 HTTP 失败、0 丢弃迭代。
2. L1 + Redis 在 200 RPS 下连续 3 轮稳定完成，每轮约 12,001 次请求；P95 中位数 3.991 ms、P99 中位数 7.499 ms，0 失败、0 丢弃。
3. 完整“购物车预览 -> 创建订单 -> RocketMQ 发布”链路以 5 个完整工作流/秒连续测试 5 轮，共完成并落库 1,503 单；0 业务失败、0 丢弃，下单接口 P95 中位数 54.806 ms、P99 中位数 61.857 ms。
4. 50 个并发请求使用同一个幂等键创建订单时，1 次首次创建、49 次幂等重放，数据库只有 1 行订单和 1 个订单 ID，所有请求成功。
5. 初测发现冷缓存 200 并发时仅 4/200 返回非空菜单。现已改为本地 SingleFlight 合并重建并结合 Redis 锁等待结果；修复后连续 3 轮均为 200/200 非空、0 错误，每轮只有 1 次完整菜单重建。详见《缓存击穿修复复测报告》。
6. 菜单 DTO 组装的加料组、咖啡豆档案和拼配档案已改为批量预加载。单次完整菜单重建 SQL 从 77 条降至 6 条，下降 92.21%；同口径 DB 直读 20 RPS 五轮测试中，平均响应中位数从 40.879 ms 降至 10.389 ms，下降 74.59%。详见《DTO转换N+1修复复测报告》。

## 2. 测试边界与隔离

- 宿主机：Windows 11，Intel Core i5-12500（6 核 12 线程），31.69 GiB 内存，Docker Desktop 4.64.0。
- 应用容器：Gateway、Order、User、Member 均限制为 1 CPU / 512 MiB。
- 专用中间件：独立 Nacos 2.2.3、RocketMQ 5.3.0 NameServer/Broker。
- 数据隔离：`cozy_perf_order`、`cozy_perf_user`、`cozy_perf_member` 三个独立 MySQL schema；Redis DB 15。
- 工具：k6 1.5.0；菜单稳态和订单稳态均使用 constant-arrival-rate 开放模型，避免闭环模型因响应变慢而自动降压。
- A/B 方法：在独立 worktree 中为菜单服务增加默认值仍为 `L1_L2` 的测试开关，分别运行 `DB_ONLY`、`REDIS_ONLY` 和 `L1_L2`；缓存击穿与 DTO N+1 修复已同步到主仓库的未提交工作区。
- 统计口径：正式 A/B 使用 5 轮中位数，不选取单轮最优值；容量测试使用 3 轮中位数。

## 3. 菜单稳态 A/B

场景：`GET /api/order/products`，20 RPS，60 秒/轮，每组 5 轮；每轮重建应用容器并在测量前完成 JVM/缓存预热。

| 模式 | 轮数 | 实际 RPS 中位数 | 平均 ms | P95 ms | P99 ms | 最大错误率 | 丢弃迭代 | MySQL 语句数中位数 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| DB_ONLY | 5 | 20.002 | 40.879 | 64.610 | 90.488 | 0% | 0 | 92,473 |
| REDIS_ONLY | 5 | 20.017 | 5.065 | 7.825 | 9.501 | 0% | 0 | 2 |
| L1_L2 | 5 | 20.017 | 3.956 | 5.909 | 8.005 | 0% | 0 | 2 |

解释：

- 相比 DB 直读，L1 + Redis 将测量区间内的 MySQL 语句数从约 92,473 降至 2，降幅 99.9978%。
- Redis-only 每轮约有 1,209 条 Redis 命令，而 L1 + Redis 中位数仅 8 条，说明进程内缓存进一步消除了网络缓存访问。
- 上表是 N+1 修复前的基线。修复后按相同 20 RPS、60 秒、5 轮口径重跑 DB_ONLY，MySQL 语句数中位数由 92,473 降至 7,208，下降 92.21%；平均/P95/P99 响应中位数分别降至 10.389/15.938/22.614 ms。

## 5. 冷/热缓存 200 并发突发

每个虚拟用户只执行 1 次请求，共 200 VU；热缓存组在开压前强制验证菜单已非空。

| 场景 | 轮数 | 每轮请求 | HTTP 失败 | 业务错误 | P95 ms 中位数 | P99 ms 中位数 |
|---|---:|---:|---:|---:|---:|---:|
| 冷缓存（修复前） | 3 | 200 | 0% | 98%（196/200 空列表） | 1,684.490 | 2,072.903 |
| 冷缓存（击穿修复后） | 3 | 200 | 0% | 0%（200/200 非空） | 3,080.361 | 3,109.009 |
| 冷缓存（再修复 N+1） | 3 | 200 | 0% | 0%（200/200 非空） | 3,474.610 | 3,495.720 |
| 已验证热缓存（击穿修复后） | 3 | 200 | 0% | 0% | 1,030.341 | 1,099.063 |
| 已验证热缓存（再修复 N+1） | 3 | 200 | 0% | 0% | 1,153.020 | 1,182.110 |

问题根因是未取得 4 个数据库重建 permit 的请求直接返回 `Collections.emptyList()`。修复后，一个实例内的并发请求等待同一次菜单重建；未取得跨实例 Redis 锁的请求以有界随机退避等待缓存，超时后执行单实例受控兜底。继续修复 DTO N+1 后，三轮仍各仅有 1 次菜单缓存更新，且单次重建 SQL 从 77 条降至 6 条。冷缓存突发的端到端 P95 未随 SQL 数量同步下降，原因是该场景还包含 200 条新连接、网关转发、单实例 1 CPU 下的大响应序列化与等待同一次重建；因此 N+1 收益以同口径 DB_ONLY 稳态 A/B 为准，不把冷突发波动包装成性能提升。

## 6. 完整下单链路稳态测试

每个工作流包含一次购物车校验/计价和一次创建订单，创建成功后发布 RocketMQ 订单事件。目标 5 工作流/秒，60 秒/轮，共 5 轮。

| 指标 | 结果 |
|---|---:|
| 完成工作流 / 新增订单 | 1,503 / 1,503 |
| 业务请求数 | 3,006 |
| 购物车平均响应中位数 | 10.233 ms |
| 购物车 P95 / P99 中位数 | 13.991 / 17.249 ms |
| 创建订单平均响应中位数 | 30.491 ms |
| 创建订单 P95 / P99 中位数 | 54.806 / 61.857 ms |
| 最大错误率 / 丢弃迭代 | 0% / 0 |

该场景用于验证完整链路的可重复稳定性，不是订单接口的最大容量测试。

## 7. 订单幂等并发测试

场景：50 VU 同时提交相同订单请求和相同 `Idempotency-Key`。

| 指标 | 结果 |
|---|---:|
| 请求 | 50 |
| 首次创建 / 幂等重放 | 1 / 49 |
| 数据库订单行 / 不同订单 ID | 1 / 1 |
| HTTP / 业务错误率 | 0% / 0% |
| 平均 / P95 / P99 | 424.994 / 532.626 / 541.653 ms |

这证明本场景下的同键并发去重成立；仍建议补充多实例、幂等处理中实例崩溃、超时重试和不同请求体复用同键等故障注入测试。
