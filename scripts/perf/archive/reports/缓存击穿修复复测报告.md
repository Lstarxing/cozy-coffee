# 菜单冷缓存并发缺陷修复复测

修复日期：2026-09-17  
源代码基线：`94361cf5316bdb9d0490f7a91645ea6dcea75389` + 本次未提交修复

## 修复内容

原实现使用 4 个许可的 `Semaphore.tryAcquire()` 限制数据库重建。冷缓存并发超过 4 时，未取得许可的请求直接返回 `Collections.emptyList()`，把“缓存正在重建”伪装成“菜单确实为空”。

本次修改为：

1. 同一应用实例使用本地 SingleFlight（同步重建区）：一个请求执行菜单重建，其他请求等待并复用其 L1 结果。
2. 其他实例未取得 Redis 分布式锁时，在 3 秒总时限内以 40～80 ms 随机间隔轮询 Redis，复用锁持有者写入的结果。
3. 锁持有者失败或超时后，每个实例最多执行一次受控数据库兜底查询，不再返回伪空菜单。
4. 保留真实空菜单的短 TTL 空值缓存；只有数据库查询结果确实为空时才返回空列表。
5. 增加 200 个并发冷 miss 的单元回归测试，断言所有结果非空，并验证顶层菜单查询只执行一次。

## 热缓存回归

首次修复后热缓存 200 VU 连续 3 轮共 600 请求，全部非空，HTTP/业务错误率均为 0，P95 中位数 1,030.341 ms。DTO N+1 修复后再次连续 3 轮共 600 请求，仍全部非空且 0 错误，P95 中位数 1,153.020 ms；约 12% 的波动没有超过本地 Docker 突发测试可合理外推的范围，因此不据此宣称热路径性能提升或退化。

## 结论与边界

单实例真实容器场景下，冷缓存 200 并发空数据缺陷已经修复，并通过 3 轮复测。Redis 分布式锁和跨实例等待逻辑已实现，但本轮没有启动多个 Order Provider 实例，因此简历可以写“冷缓存 200 并发验证通过”，不应进一步写成“已完成多实例故障注入验证”。
