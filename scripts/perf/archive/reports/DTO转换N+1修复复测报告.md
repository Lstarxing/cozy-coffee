# 菜单 DTO 转换 N+1 修复复测

修复日期：2026-09-17  
源代码基线：`94361cf5316bdb9d0490f7a91645ea6dcea75389` + 本次未提交修复

## 根因与修复

菜单查询先获取 31 个商品，随后 DTO 转换对每个商品分别查询加料组及绑定关系，并逐条查询咖啡豆档案和拼配档案，导致一次完整菜单重建产生 77 条 SQL。缓存命中时问题会被掩盖，但冷重建和 DB 直读模式存在明显读放大。

本次修改为：

1. `ProductAddonResolver` 一次按全部商品 ID 查询加料组，再按全部组 ID 查询绑定关系，最后按全部加料 ID 批量读取加料数据，并在内存中回组装。
2. `OrderDtoConverter` 新增列表批量转换入口，对咖啡豆档案和拼配档案分别收集去重 ID 后使用 `selectBatchIds` 预加载。
3. `MenuCacheService` 在完整菜单重建时调用批量转换入口；单商品详情仍保留原入口，避免改变既有调用约定。
4. 新增两商品共享关联数据的单元测试，验证每类关联只执行 1 次批量查询，并断言不再调用逐条 `selectById`。

## 自动化测试

## 单次冷重建 SQL

| 状态 | 轮数 | 每轮非空响应 | 业务错误率 | 每轮缓存更新 | SQL/完整重建 |
|---|---:|---:|---:|---:|---:|
| N+1 修复前 | 3 | 200/200 | 0% | 1 | 77 |
| N+1 修复后 | 3 | 200/200 | 0% | 1 | 6 |

SQL 从 77 条降至 6 条，下降 92.21%。修复后三轮检查均为 600/600 通过，HTTP 与业务错误率均为 0。

测试接口为 `GET /api/order/products`，固定 20 RPS、60 秒/轮，各版本 5 轮；每轮重建应用并预热 100 次。旧版本结果来自同一隔离环境已归档的正式基线，新版本按相同口径重跑。

|---|---:|---:|---:|
| 实际 RPS | 20.002 | 20.016 | 持平 |
| 平均响应 | 40.879 ms | 10.389 ms | 降低 74.59% |
| P95 | 64.610 ms | 15.938 ms | 降低 75.33% |

修复后五轮均完成约 1,200 次请求，无 HTTP 失败、无业务错误、无丢弃迭代。

## 冷/热 200 VU 回归说明

N+1 修复后，冷缓存三轮 P95 中位数为 3,474.610 ms，热缓存三轮 P95 中位数为 1,153.020 ms，均保持 0 错误和 100% 非空。端到端突发延迟没有随 SQL 数量等比例下降，因为该场景还包含 200 条新连接、网关转发、1 CPU 容器的大响应序列化及并发请求等待同一次重建。故性能收益采用 DB_ONLY 同口径稳态 A/B 数据，不用突发场景的自然波动夸大收益。

## 结论与边界

菜单 DTO 冷路径的关联查询已由随商品数增长的逐条查询改为固定批次查询，并通过单元测试、单次冷重建 SQL 计数和 DB 直读五轮 A/B 三重验证。当前 31 个商品数据集下完整重建为 6 条 SQL；若未来新增其他逐项关联，仍需用 SQL 计数回归测试守住该边界。
